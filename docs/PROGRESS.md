## Phase 2 — the glue harness (2026-10-15)
Goal: one harness that pools Claude, Codex and Cursor subscriptions. You type what you want; harness picks the agents, keeps one shared memory, and a lead agent tracks the team and sets small follow-up jobs.

- [x] **M16 Launch screen** — the big block-letter HARNESS banner and welcome card on every launch (not only on an empty project), until you start typing.
- [x] **M17 Auto-routing** — no `@role` tagging: `/task` and direct work go to the right agent from role guides and folder scopes; the planner only runs when work spans agents.
- [x] **M18 Team board (HARNESS.md)** — one unified `.harness/HARNESS.md` regenerated from events: goal, who is working on what, what each finished agent did and changed, notes agents leave (`NOTE:` lines), open problems. Every agent prompt carries it.
- [x] **M19 Context handoff** — dependent tasks get their dependencies' summaries and changed files; sessions over a context budget restart fresh from the board + handoff instead of resuming into a compacted context.
- [x] **M20 Lead (compiler) agent** — a read-only `lead` role that, when a batch of chat work settles, reads the board and returns a status line and at most a few small follow-up jobs (validated, capped, auto-approved, bounded depth).
- [x] **M21 Subscription pooling** — a role may list more routes (`pool: [codex, cursor]`); each task goes to the route with the most headroom, so work flows across subscriptions instead of stopping at one limit.
- [x] **M22 Model tiers** — a route may map task sizes to models (`models: {S: haiku, M: sonnet, L: opus}`); the planner's size picks the model.
- [x] **M23 Land** — `/land` brings finished integration work into your branch; an integration branch with no shared history with the base is rebuilt from it.
- [x] **M24 Fresh daemon** — the daemon reports which build it runs; the CLI restarts a daemon started from an older build of the same entry file when no agent is mid-run (and says so when runs are in flight), so `harness` never talks to old code after a rebuild.
- [x] **M25 Agent terminals** — one real terminal window per agent: `harness watch <agent>` streams an agent's live session in any terminal, and `/windows` opens one per agent.
- [x] **M26 Faster reviews** — the review prompt asks for a verdict from the diff, not a repository audit; `limits.review_sizes` (setup writes `[M, L]`) lets small tasks merge once harness's own checks pass.
- [x] **M27 Docs** — README and `/help` describe routing, the board, the lead, pools, tiers, watch and land.
- [x] **M28 Live team run** — `scripts/live-team.sh` (real Claude, Codex if signed in) passed on 2026-10-15: `harness tell` routed a server task straight to `backend` with no planning run, Claude implemented it, harness's checks passed, the agent's `NOTE:` lines reached the board, the lead (real Claude) re-ran the tests and reported the request done, and `harness land` fast-forwarded `main`.
- [x] **M29 Parallel live run** — `scripts/live-team.sh "<server + web request>"` on 2026-10-15: the planner (Claude) split it in 14s into a backend and a frontend task that ran at the same time on Claude and Codex (16s and 30s), both merged, the lead (Claude) verified all 7 tests in 19s, and `land` fast-forwarded main: about 65 seconds end to end, against ~11 minutes for the serialized run that started phase 2. The board now shows repo paths instead of agents' absolute worktree links.
- [x] **M30 Config upgrade** — `harness setup --upgrade [--pool] [--dry-run]` adds what newer versions use (role descriptions, a lead on the planner's route, `review_sizes: [M, L]`) to an existing harness.yaml, keeping comments and edits; `--pool` lets each writer also use one route of every other vendor. Idempotent and validated before writing.
- [x] **M31 Usage you can trust** — Codex exact usage from its app-server (no quota spent); Claude readings shared across projects per account and kept across restarts; Cursor manual-budget hint; pools refresh usage right before ranking and count manual budgets.
- [x] **M32 Agent-resolved conflicts** — on a merge conflict, harness replays the task onto the latest integration branch with `git apply --3way` (markers in files, nothing in progress) and the task's agent resolves them in its own session; a built-in `conflict-markers` gate check blocks any leftover markers; a second conflict goes to the person.
